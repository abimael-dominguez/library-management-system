Title: Serverless LMS Web Application (AWS)

Objective:
- Build a serverless Library Management System (LMS) web application with a static frontend hosted on S3 and a backend implemented using AWS Lambda functions, fronted by API Gateway. Infrastructure is defined via AWS CloudFormation. Local development uses Docker.
  - Prioritize a minimal, cost-efficient infrastructure: use only essential AWS resources, prefer on-demand models, avoid VPC unless strictly required, and design for low request volume cost (optimize cold starts, small packages, minimal GSIs).

Scope & Requirements:
1) Cloud Platform & Languages
- Cloud: AWS.
- Frontend languages: English (US) and Spanish (Mexico) i18n support.
  - Backend: Serverless-first using AWS Lambda functions with API Gateway, Pydantic for validation, and DDD/Clean Architecture for structure (no Django).

2) Architecture & Project Scaffolding
- Follow Clean Architecture principles and Domain-Driven Design (DDD).
- Provide a scaffolder (scripts or documented steps) to generate the project structure.
- Organize code into clear layers with directories named to reflect DDD:
  - domain: Entities, value objects, domain services, aggregates, repositories (interfaces).
  - driven: Infrastructure adapters (DynamoDB repositories, external services, AWS SDK integrations).
  - design: Application services/use-cases, DTOs, validators, API handlers, and composition roots (DI wiring).
- Place Lambda handlers within appropriate layer folders (usually in design for API handlers calling domain services, with driven for infra implementations).

3) Frontend
- Use Tabler (Repo 2) as design reference for UI components and layout.
- Host static assets (HTML/CSS/JS) in S3 bucket named: lms-static-data.
- Provide i18n mechanism for EN-US and ES-MX (strings structure and toggling).
- Implement a search page with autocomplete (books by title, author, ISBN, category).
- Ensure UX is optimized for fast loans/returns workflow: quick search/autocomplete for books and users/members; minimal clicks; clear status feedback.

4) Data Layer
- Use Amazon DynamoDB.
- Translate the PostgreSQL schema and relationships from create_tables.sql to a DynamoDB data model.
  - Define partition/sort keys, GSIs/LSIs, item structure, and access patterns for typical LMS operations (books, users, loans, returns, reservations, fines, etc.).
  - Document the mapping rationale from relational to NoSQL.

5) Backend (Serverless)
- Implement backend logic via multiple small AWS Lambda functions (not a single monolith) to simplify maintenance.
- Suggest a sensible Lambda decomposition (e.g., Users, Books, Loans, Returns, Reservations, Fines, Auth) aligned to API routes.
- Use API Gateway to expose RESTful endpoints.
- Use Pydantic for request/response validation and data models inside Lambdas.
- Apply an interface-based design pattern:
  - Define abstract interfaces (contracts) for services (e.g., BookService, UserService, LoanService).
  - Provide concrete implementations (e.g., DynamoBookService) and inject dependencies/parameters.
- If necessary, provision a VPC and its networking (subnets, routing, security groups) to support private resources.
- Implement core LMS features:
  - Register loans (Préstamos): change book status to "Prestado".
  - Register returns (Devoluciones): change book status to "Disponible".
  - Create employees (staff managing the library; see Repo 1 terminology).
  - Create users/members (borrowers; "member" in English).
  - Register new books.
- Autocomplete endpoints to support fast workflows for loans/returns (by title, author, ISBN) and for selecting members/employees.

6) Infrastructure as Code
- Provide AWS CloudFormation templates in the repository to define:
  - S3 bucket (lms-static-data)
  - API Gateway (routes, integrations, stages)
  - Lambda functions (roles, permissions, env vars)
  - DynamoDB tables (schema, GSIs)
  - Optional VPC and networking (only if required)
- Ensure the templates support redeploys, rollbacks, and parameterization for environments.
  - Cost Optimization Principles:
    - Prefer on-demand Lambda and DynamoDB.
    - Keep Lambda packages small; avoid heavy dependencies.
    - Minimize number of API Gateway routes; consolidate where sensible.
    - Limit GSIs to proven access patterns; add more only if justified.
    - Avoid VPC unless accessing private resources.
    - Enable logging at minimal required levels and use retention policies.
  - If using AWS SAM, include full templates and metadata (`template.yaml`, parameter files), and document exact commands for build/deploy/rollback/delete.

CLI & AWS Profile
- Use AWS CLI for all cloud operations and deployments.
- Use the named profile: `immersion` (configured in the user's ~/.aws credentials/config).
- Example: `aws --profile immersion cloudformation deploy ...` and `sam deploy --guided --profile immersion`.

9) Assumptions & Constraints
- Authentication/authorization: If not specified, propose a simple approach (e.g., API keys, Cognito, or JWT) and modularize to allow future upgrades.
- Performance and cost: Favor efficient access patterns and small Lambda packages. Keep cold start considerations in mind.
- Testing: Include unit tests for Lambdas and Pydantic validation. Provide minimal integration tests for key flows (e.g., create loan, return book).
  - Cost: Favor minimal infrastructure footprint; document estimated monthly costs and how to scale economically.
  - Usage profile: Expect on-demand usage with peaks of ~1000 queries on Wednesdays and ~1000 queries on Sundays; minimal usage outside these windows. Design for true on-demand (no always-on services), leveraging Lambda/API Gateway scaling and DynamoDB on-demand.
  - Current and projected data size: DynamoDB will hold fewer than ~500 items initially and grow slowly (~+20 items per week). Optimize table design and GSIs for small datasets and low cost; avoid over-indexing.

11) Testing Requirements
- Unit tests: Cover core domain logic, Pydantic models (validation and serialization), and service interfaces with DynamoDB repository stubs/mocks.
- Integration tests: Validate end-to-end flows locally (e.g., préstamos and devoluciones) via `sam local` or equivalent, including API Gateway routing and Lambda handlers.
- Provide fixtures and sample data for books, members, and employees.
- Ensure tests are fast and deterministic, suitable for CI and local runs.
